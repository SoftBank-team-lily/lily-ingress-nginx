# lily-router 설계

기준: 인프라 실측 그림 `Lily AWS Infra.png` (2026-10-01), 각 레포 `main` (2026-10-02).
API 명세는 [api/01-Ingress Nginx API.md](<api/01-Ingress Nginx API.md>), 배경은 [01-Ingress Nginx 모듈화.md](<01-Ingress Nginx 모듈화.md>).

---

## 1. 한 줄 정의

**lily-router 는 클러스터 안 앱의 "접근 경로"를 관리하는 모듈이다.**
배포 모듈에게서 서비스 이름과 접근 경로를 받아 k8s Ingress 로 반영하고, 다른 모듈이 물으면 앱 주소·배포 상태·파드 위치를 알려 준다.
트래픽 자체는 처리하지 않는다 (프록시는 ingress-nginx).

| 하는 일 | 하지 않는 일 (담당) |
|---|---|
| 앱별 라우트(주소 × 경로 → Service) 저장과 Ingress 반영 | 빌드·배포·슬롯 전환 (builder, cicd) |
| canary 입구(가중치) 열기·올리기·닫기 | 노드 결정 (k8s 스케줄러) |
| 추가 주소(nip.io, 커스텀 도메인) 관리 | `{app}.lilycloud.kr` DNS·CNAME 전환 (builder `AppAddress`, Cloudflare) |
| 호스트 충돌 검사 | HTTPS 인증서 (ALB·ACM, Cloudflare) |
| 라우트·파드 위치 조회 API | 지표 수집·장애 판정 (observer) |
| ingress-nginx 설치 설정 관리 (6장, 제안) | 사용자 트래픽 프록시 (ingress-nginx) |

## 2. 배치

```
                 Cloudflare ({app}.lilycloud.kr)
                        │
                     lily-alb  HTTPS 443 종료 (ACM)
                        │ HTTP 80 (대상 그룹 lily-workers)
        ┌───────────────┴───────────────┐
┌───────▼────────┐              ┌───────▼────────┐
│ lily-worker-1  │              │ lily-worker-2  │
│ svclb 80·443 ──┼──────────────┼▶ ingress-nginx │◀─┐ watch (Ingress, EndpointSlice)
│ 앱 파드         │◀─────────────┼── 앱 파드       │  │
└────────────────┘   프록시      └────────────────┘  │
                                                    │
┌───────────────────────────── lily-server (control-plane) ─┴───────┐
│  k3s API :6443  ◀── Ingress 쓰기 ──  lily-router  (lily-system)    │
│                                       ▲   ▲   ▲   ▲               │
│                         HTTP+Bearer   │   │   │   │               │
│        lily-cicd ─────────────────────┘   │   │   │               │
│        lily-web (frontend) ───────────────┘   │   │  조회          │
│        lily-builder ──────────────────────────┘   │               │
│        lily-observer ─────────────────────────────┘               │
└────────────────────────────────────────────────────────────────────┘
```

| 항목 | 결정 | 이유 |
|---|---|---|
| 위치 | **lily-server (control-plane) 고정**, namespace `lily-system` | 부르는 쪽(cicd, web, builder, observer)과 k3s API 가 모두 여기 있다. builder·observer 와 같은 방식(`nodeSelector` + toleration) |
| 레플리카 | 1 | 같은 앱의 읽고-고치고-쓰기를 프로세스 안에서 직렬화한다. 멈춰도 이미 쓴 Ingress 는 남아 사용자 트래픽에는 영향이 없다 (5장) |
| 노출 | ClusterIP `lily-router.lily-system.svc:80` → 컨테이너 8075 | 클러스터 밖에서 부를 일이 없다. ALB·nip.io 에 열지 않는다 |
| 권한 | ClusterRole: `ingresses` 읽기·쓰기, `endpointslices` 읽기 | 앱 namespace 가 정해져 있지 않다 |
| 자원 | 요청 cpu 50m, mem 256Mi / 상한 384Mi | t3.medium 한 대에 플랫폼 컴포넌트가 모여 있다. 올리기 전 `kubectl top node` 로 여유 확인 |

ingress-nginx 가 몇 개, 어느 노드에 있든 라우터는 k3s API 에 Ingress 를 **한 번만** 쓴다. 각 컨트롤러가 watch 로 읽어 간다.

## 3. 데이터

### 3.1 원본 저장 위치: Ingress 어노테이션 (DB 없음)

| 리소스 | 내용 |
|---|---|
| `{app}-ingress` | 라우트 전체. 어노테이션 `lily.io/route` 에 원본 JSON (`RouteState`) |
| `{app}-canary-ingress` | canary 가 열려 있을 때만. 가중치는 `canary-weight` 어노테이션 |
| 공통 레이블 | `app.kubernetes.io/managed-by: lily-router`, `lily.io/app`, `lily.io/role: main\|canary` |

이름은 lily-cicd 가 쓰던 것과 같다. observer 가 지표를 `ingress="{app}-ingress"` 라벨로 조회하므로 **바꾸지 않는다.**

`RouteState`:

| 필드 | 누가 정하나 | 재배포 시 |
|---|---|---|
| `serviceName`, `servicePort`, `primaryHost`, `paths`, `timeoutSeconds` | 배포 모듈 (`PUT /routes`) | 덮어씀 |
| `deployment` (strategy, slot, version, image, nodes, status) | 배포 모듈 | 덮어씀 |
| `extraHosts` | 운영자 (`POST /hosts`) 또는 이어받기 | **유지** |
| `keptAnnotations`, `tls` | 이어받기 (다른 주체가 만든 Ingress) | **유지** |

DynamoDB(플랫폼 메타데이터) 대신 Ingress 에 두는 이유:
- 실제 라우팅과 원본이 한 리소스에 있어 어긋나지 않는다 (Ingress 를 지우면 라우트도 없다)
- AWS 권한·SDK 가 필요 없다. lily-cicd `ReleaseStore` 와 같은 방식

### 3.2 실시간 정보 (저장하지 않음)

`backends` 는 조회할 때마다 EndpointSlice 에서 읽는다: 파드 이름, IP, **노드(lily-worker-1/2)**, Ready.

## 4. 모듈 간 흐름

호출 방향은 항상 **다른 모듈 → lily-router**. 라우터는 다른 모듈을 부르지 않는다.

### 4.1 블루그린 배포 (기본 전략)

```
lily-cicd                                 lily-router                       k8s
  │ 슬롯 green 배포·Ready                                                     
  │ canary 판정 (Service 에 직접 요청, 사용자 트래픽 없음)
  │ GET /routes/{ns}/{app} ─────────────▶ host 확인 (없으면 판정 건너뜀)
  │ Service selector → green                                   
  │ PUT /routes/{ns}/{app} ─────────────▶ RouteState 계산 ─────────▶ {app}-ingress 쓰기
  │   {serviceName, host, deployment}     (처음이면 기존 Ingress 이어받기)      │ ingress-nginx watch
  │ ◀──────────── 200 {url, hosts, backends}                                ▼ 수 초 안에 반영
  │ 이전 슬롯 scale 0
```

`{app}-svc` 의 selector 만 바뀌므로 Ingress 내용은 같다. 첫 배포와 호스트가 바뀔 때만 Ingress 가 실제로 달라진다.

### 4.2 canary 전략 (`LILY_DEPLOY_STRATEGY=canary`, 지금 꺼짐)

```
lily-cicd                                          lily-router
  │ 두 슬롯 Ready, {app}-canary-svc 생성
  │ PUT /routes/{ns}/{app}/canary {canary-svc, 0}  ─▶ {app}-canary-ingress (weight 0)
  │    (404 = 라우트 없음 → PUT /routes 후 다시)
  │ PUT .../canary {weight: step} … 100             ─▶ weight 갱신
  │ 본 Service 를 새 track 으로
  │ DELETE /routes/{ns}/{app}/canary                ─▶ canary Ingress 삭제
  │ PUT /routes/{ns}/{app}                          ─▶ 라우트 갱신
```

canary 는 라우트의 **모든 주소**에 같은 비율로 걸린다 (지금 cicd 는 이번 배포 호스트 하나에만).

### 4.3 그 밖의 호출

| 상황 | 부르는 쪽 | 호출 |
|---|---|---|
| cicd 재시작 뒤 남은 canary 정리 | cicd `DeployRecovery` | `GET /routes?canary=true` → 진행 중 배포가 없으면 `DELETE .../canary` |
| 앱 삭제 | cicd `AppRemover` | `DELETE /routes/{ns}/{app}` |
| 대시보드 라우팅·canary 표시 | lily-web (`INGRESS_API_URL`) | `GET /routes/{ns}/{app}` |
| 앱 목록의 접속 주소 | builder `ClusterApps`, observer `KubernetesClusterSource` | `GET /routes` |
| nip.io·커스텀 도메인 추가 | 운영자 | `POST /routes/{ns}/{app}/hosts` |
| 플랫폼 Ingress (`lily-builder-burst` 등) | 운영자 | `PUT /routes/lily-system/{name}` (경로·타임아웃 포함) |

### 4.4 내 PC 로 옮기기 (builder `AppAddress`)

`{app}.lilycloud.kr` 의 CNAME 을 ALB 에서 Cloudflare 터널로 바꾸는 일이라 **라우터는 관여하지 않는다.**
옮긴 뒤에도 클라우드 쪽 라우트는 남아 있어 되돌리기(CNAME → ALB)만 하면 바로 받는다.

## 5. 장애·예외 처리

| 상황 | 영향 | 처리 |
|---|---|---|
| 라우터 Pod 중지 | 사용자 트래픽 **영향 없음** (Ingress 는 k8s 에 남음). 새 배포의 라우트 변경만 실패 | cicd `HttpTrafficRouter` 가 짧게 재시도 (3회, 0.2·0.4·0.8초). 끝내 실패하면 배포 FAILED + "router 적용 실패" (지금 `route()` 실패와 같음) |
| 라우터 응답 전 연결 끊김 | 반영됐는지 모름 | 모든 PUT·DELETE 는 멱등. 같은 요청을 다시 보낸다 |
| 호스트·경로 충돌 | 반영 안 됨 | `409 HOST_CONFLICT`. 다시 보내지 않는다 (4xx) |
| k8s API 실패 | 반영 안 됨 | `502 KUBERNETES_ERROR`. 다시 보내도 된다 (5xx) |
| ingress-nginx 반영 지연 | 200 직후 몇 초는 이전 설정 | 문서화. 반영을 확인해야 하면 실제 주소로 요청해 본다 |
| ingress-nginx 컨트롤러 1개(worker-2) 중지 | **전체 앱 접속 불가** | 6장 R3 (워커마다 컨트롤러) |

## 6. 보안·네트워크

| # | 항목 | 내용 |
|---|---|---|
| S1 | 인증 | `/api/` 전체 `Authorization: Bearer {LILY_ROUTER_API_TOKEN}`. Secret `lily-router-token` 을 라우터와 부르는 모듈이 같이 읽는다. `/healthz` 만 열림 |
| S2 | NetworkPolicy | `lily-system` 은 외부 유입이 막혀 있다고 되어 있으나(builder 매니페스트 주석) 정책이 레포에 없다. 라우터 매니페스트에 **lily-cicd, lily-web, lily-builder, lily-observer → lily-router:8075 만 허용**하는 정책을 넣는다 |
| S3 | 외부 노출 금지 | 라우터 API 를 Ingress 로 열지 않는다. 열면 누구나 라우트를 바꿀 수 있다 |
| S4 | nip.io 경로 | lily-server EIP 로 TLS 없이 바로 들어온다 (ALB 우회). 라우터는 nip.io 를 추가 주소로만 다루고, 새로 추가하지 않는 것을 기본으로 한다 |

## 7. ingress-nginx (라우터 모듈이 맡을 것을 제안)

지금 ingress-nginx 는 손으로 설치되어 있고 설치 기록이 어느 레포에도 없다.
라우터가 쓰는 Ingress 를 실제로 처리하는 쪽이므로 설치 설정을 이 레포 `deploy/ingress-nginx/` 에 둔다.

| # | 내용 | 이유 |
|---|---|---|
| R3 | 컨트롤러를 **워커마다 1개** (DaemonSet, `nodeSelector: node-role.kubernetes.io/worker`) | 지금은 worker-2 하나. 죽으면 전체 장애 |
| R3-1 | `--enable-metrics=true` 유지 | observer 지표 출처. v1.12 부터 기본 꺼짐, 10-01 에 kubectl patch 로 켬 (observer README) |
| R3-2 | 서비스 노출은 지금처럼 LoadBalancer(svclb) 80·443 | ALB 대상 그룹(워커:80)·nip.io(server EIP:80) 를 바꾸지 않는다 |
| R3-3 | 버전 v1.12.1 고정 | 지금과 같게 |

운영 중인 컨트롤러를 바꾸는 일이라 **설정을 먼저 레포에 남기고, 적용은 따로 합의**한다.

## 8. 그림·코드 차이로 확인할 것

| # | 내용 | 영향 |
|---|---|---|
| C1 | 그림(10-01): Cloudflare **DNS만**, 주소 `{앱}.apps.lilycloud.kr` / 코드(10-02): **프록시 CNAME**, `{app}.lilycloud.kr` | 라우터 기본 도메인은 코드 기준 `lilycloud.kr` 로 맞춤. 그림 갱신 필요 |
| C2 | ALB 인증서가 `*.apps.lilycloud.kr` (ACM). `{app}.lilycloud.kr` 은 이 인증서에 맞지 않는다 | Cloudflare 프록시 SSL 모드가 Full(strict) 이면 Cloudflare → ALB 구간이 실패할 수 있다. ACM 에 `*.lilycloud.kr` 이 있는지, SSL 모드가 무엇인지 확인 (라우터 범위 밖, 접속에는 영향) |
| C3 | lily-cicd 매니페스트에 `nodeSelector` 가 없다 | 그림에서 control-plane 에 있는 것이 설정이 아닐 수 있다. cicd 담당에 공유 |

## 9. 구현 현황과 남은 일

| 구분 | 상태 |
|---|---|
| API 11개, Ingress 반영, 이어받기(호스트·TLS·어노테이션), 충돌 검사, canary(0~100), backends | 완료 (`main`) |
| 배치 고정 (2장), NetworkPolicy (S2) | **할 일** — 라우터 매니페스트 |
| cicd 연동: `TrafficRouter` 확장, `HttpTrafficRouter`, Ingress 직접 조작 6곳 교체, 재시도 (5장) | **할 일** — cicd 레포 브랜치 |
| builder `ClusterApps`, observer `KubernetesClusterSource` 의 URL 을 라우터에서 | 할 일 (cicd 다음) |
| lily-web `INGRESS_API_URL` 설정 | 배포 설정만 |
| ingress-nginx 설치 설정 (7장) | 제안 |
| 주소마다 다른 경로 | 한계 (builder 처럼 주소마다 열린 경로가 다르면 앱을 나눠 등록) |

## 10. 검증 계획 (로컬 k3d, 운영과 같은 모양)

```
k3d cluster create lily --servers 1 --agents 2      # lily-server 1 + worker 2
```

1. 서버 노드에 control-plane taint, 에이전트에 `node-role.kubernetes.io/worker=worker` 레이블 (운영과 같게)
2. ingress-nginx v1.12.1 (7장 설정) 설치
3. lily-router, lily-cicd(`LILY_ROUTER_URL` 설정) 를 `lily-system` 에 배포 (이미지는 k3d 에 직접 import)
4. lily-blog-sample 을 cicd API 로 두 번 배포 (blue → green)
5. 확인

| 확인 | 기대 |
|---|---|
| 라우터·cicd Pod 위치 | 서버 노드 |
| `GET /routes/default/blog` | `url`, `deployment.slot=green`, `backends[].node` 가 에이전트 |
| `curl -H 'Host: blog.lilycloud.kr' http://localhost:<lb>/version` | green 응답 |
| 재배포 전 nip.io 를 `POST /hosts` 로 추가 → 재배포 | nip.io 유지 |
| 라우터 Pod 를 지운 채 앱 요청 | 계속 응답 (Ingress 유지) |
| canary 전략으로 한 번 배포 | weight 0 → … → 100, 끝나면 canary Ingress 없음 |
| `DELETE /api/apps/blog` (cicd) | 라우트 삭제 |
